# Obsidian Export — snapshot format and behavior (proposed v1)

**Status:** PROPOSED specification for slice SB-2 of [ADR-0005](../adr/0005-governed-second-brain-architecture.md); no exporter exists. **Revision 3 (2026-10-20, founder simplification):** the export is a one-shot, user-requested **snapshot** — a ZIP or a newly created folder — not a managed, continuously reconciled projection. Revision 2's registry, write-lock fence, ownership hashes and automatic Forget cleanup are removed (§11.5, Codex N1–N2). Kept: inert serialization (Codex F3), scope and reference closure (F4) with typed structural verification (N3), byte-limited filenames (N4), and the Animate correction (F6), all reflected in the [validation spec §4](SECOND-BRAIN-VALIDATION.md#4-obsidian-snapshot-export-sb-2). Founder decisions it depends on: D7, D12, D13 and D15; D8, D9 and D14 are settled by the 2026-10-20 direction (ADR-0005 §15). The file keeps its name so links stay stable; "projection" elsewhere means an exported snapshot. The [demo vault](obsidian-demo-vault/) is a hand-written instance of this format.

## 1. Purpose and non-goals

**Purpose:** let the person explore Sovereign's knowledge visually and navigably in Obsidian — Graph view, Local graph, Backlinks, search — and answer "what is connected to this, why, and since when?" from the notes themselves.

**What it is:** an optional, human-facing snapshot viewer. The user explicitly asks for an export; Sovereign reads one authorized snapshot of its canonical vault, renders ordinary Markdown notes with working `[[wikilinks]]`, verifies them, and hands them over as a ZIP or a newly created folder that the user opens as an Obsidian vault. To see newer memory, the user exports again. A manual CLI comes first; a later UI button may call the same operation (§12).

**Non-goals:** an export is not a canonical database, not an always-current replica, not a synchronized memory subsystem, not a backup, not an editing surface, not a source of authority, and **not a security boundary that enforces Forget across exported copies** (§11.2). Removing Obsidian or an export changes nothing in Sovereign.

## 2. What an export may contain

Only canonical state, rendered deterministically. "Today" means derivable from the current schema once the exporter exists; the V0 exporter renders only those rows.

| Element | Canonical basis | Available |
| --- | --- | --- |
| Source notes: content, stored time, active/superseded, sensitivity | `records` | Today |
| Revision chains (`CORRECTS` / `CORRECTED_BY`) | `records.supersedes_id` | Today |
| Claim notes: text, status, support, authority, origin | `claims`, `claim_sources`, derived support | Today |
| `SUPPORTED_BY` links (verified evidence only, §8) | `claim_sources` | Today |
| Claim supersession chains (`SUPERSEDES` / `SUPERSEDED_BY`) | `claims.supersedes_id` | Today |
| Decision history per claim | `claim_events` | Today |
| Timeline and status index notes | Stored and decision times | Today |
| Note titles | None: derived from the item's own text (§5) | Today, with D7 privacy rules |
| Project and concept hubs, membership | Human-declared organization | After SB-3 (D2) |
| Decisions as their own folder | A claim form/kind | After SB-3 or SB-7 |
| Typed domain relations | Structured MemoryClaims | After SB-7 (D3) |
| `valid_from` / `valid_until`; correction vs change | Temporal claim extension | After SB-6 (D10) |

Anything not in this table — model summaries, inferred entities, project nodes the schema does not hold, co-occurrence links, similarity links — is **not** exported. Records carry no import marker, so an export cannot truthfully say whether a record was captured or imported; it says "stored".

## 3. Obsidian capabilities this format relies on

Core features only, checked against Obsidian's published help; every behavior the guarantees depend on must be verified natively per supported version before SB-2 is accepted (validation spec §4.2; not yet executed, §4.6).

- **Graph view / Local graph:** one line per linked note pair; *Arrows* shows direction; *Groups* color nodes by a search query; a filter query hides notes; *Tags* and *Orphans* toggles; Local graph depth. **Node labels are note names, i.e. filenames.**
- **Animate:** shows notes appearing in file-creation order on that disk. It is **not** a history view: it knows nothing of stored times, corrections, supersessions or MemoryClaim status changes, and the exporter makes no attempt to control it. Chronology is in the Timeline and decision-history notes (§9).
- **Backlinks pane:** incoming links for the open note — the reverse direction of every relationship without writing reverse links.
- **Properties:** YAML frontmatter is shown and searchable. A quoted `"[[...]]"` property value is a documented internal link, so no property value may ever contain link syntax (§6); graph-relevant links live in the note body only.
- **Not available:** edge labels, edge properties, per-edge colors, typed or temporal edges, clicking an edge.

## 4. Export layout

```text
<export root>/                          a new folder created by the export, or the single top folder inside the ZIP
  .sovereign-export.json                format, an export_id derived from the export key, and the snapshot time only
  _Navigation/                          hidden from the default graph by tag
    Start Here.md                       snapshot time, class-level scope, legend, how to refresh, the Forget boundary
    Timeline.md                         stored and decision events of included items
    Claims by status.md                 approved / stale / orphaned / contested / proposed / superseded / rejected
  Projects/   Concepts/                 hubs (after SB-3)
  Sources/                              one note per record revision
  Claims/     Decisions/                one note per claim (Decisions/ once a claim form exists)
  Relationships/                        one note per structured relation claim (after SB-7)
  .obsidian/graph.json                  default graph settings, constants only (§10)
```

The fixed set of kind folders is created in every export, empty or not, so a folder's existence reveals nothing. Sovereign keeps no record of an export after it finishes: no registry, no per-file hashes, no list of exports (§11.4).

## 5. Identity, handles, filenames and titles

- **Handle:** each export draws a fresh random key `k_E`, held in memory only and discarded when the export finishes. An item's handle is its kind letter, a hyphen and the first 8 characters of the lowercase base32 encoding of HMAC-SHA256(`k_E`, `sovereign-projection/v1` NUL kind NUL canonical ID). Handles cannot be computed by anyone who only guesses an ID, and they differ between exports, so two exports cannot be correlated by handle and nothing needs to be stored to recompute them. Uniqueness is checked case-insensitively **within the authorized set only**; a colliding handle is extended one character at a time until it is unique. The marker's `export_id` is the first 16 characters of the lowercase base32 encoding of HMAC-SHA256(`k_E`, `sovereign-export-id/v1`), so it is unpredictable yet fixed by the key.
- **Identity in the note:** `sovereign_handle` only (D13 recommendation); the raw canonical ID is never written into an export. Imported, restored and legacy IDs can be arbitrary, sequential or meaningful text, and even canonical-UUID IDs can be enumerable (ordinary import derives claim IDs with a public UUIDv5 namespace, and import or restore can supply sequential UUID-shaped IDs), so any written raw ID could reveal a gap where an excluded item sits. If the founder chooses to write canonical UUIDs anyway, that residual is stated in the preview.
- **Filename (D7):** `<title> (<handle>).md`; opaque mode `<handle>.md`. Graph labels are filenames, so readable titles make the graph usable; filenames also appear in OS listings, search indexes, ZIP listings, backups and sync logs, which is a disclosure surface. Only the final parenthesized token is generated.
- **Title:** from the item's **own text only** — never from a neighbour (except relationship titles, composed below only from endpoints inside the authorized set after naming closure, §8.3), never an ordinal, chain position or "N of M". Take the first non-blank line; apply NFC; keep — always excluding default-ignorable code points (including variation selectors and U+034F) and the Hangul fillers U+115F, U+1160, U+3164, U+FFA0 — characters of Unicode general categories Lu, Ll, Lt, Lm, Lo and Nd, and combining marks (Mn, Mc) that directly follow a kept letter, digit or mark, at most three in a row (so Japanese, Devanagari, Thai or pointed Hebrew titles stay readable), plus space, `-`, `.`, `,`, `'` and `&`; map everything else to `-` (so `` ( ) _ [ ] ! # ^ | < > ` * ~ % $ : = { } \ / `` and all other symbols can never form syntax or imitate a handle); collapse runs; strip leading and trailing space, `.` and `-`; apply NFC again to the sanitized result; then **truncate by extended grapheme clusters** (below) to at most 60 clusters **and** to the byte budget of *Filename length*; use `Untitled <kind>` if the result is empty; prefix `Item ` to a Windows reserved device name. Relationship titles are composed from their endpoints' titles and the predicate's fixed display phrase from the versioned predicate registry (for example *Project Harbor depends on Project Lantern*); the phrase itself satisfies this rule, so a predicate constant such as `DEPENDS_ON` never appears in a title or filename (only in the generated predicate line and the `predicate` property). Two revisions of one record usually share a title; their handles and status tell them apart.
- **Filename length (Codex N4):** the complete basename — title, the separator ` (`, the handle **after** any collision extension, `)` and `.md` — must be at most **140 bytes in UTF-8**, which fits the common 255-byte limits and the 143-byte limit of some encrypted filesystems. Handles are assigned first, collision extensions included; the title then gets the remaining budget, measured in bytes (a CJK character is 3 bytes, a CJK Extension B character 4).
- **Truncation by extended grapheme clusters (Codex N4):** the sanitized, NFC title is segmented into **extended grapheme clusters** as defined by Unicode Standard Annex #29 (*Unicode Text Segmentation*), using the Unicode version the exporter pins for NFC, general categories and segmentation alike. The title keeps the longest prefix of **whole** clusters that has at most 60 clusters and whose UTF-8 encoding fits the byte budget; if that prefix contains a space, it is cut back to the last space; the trailing strip above is applied again. A cut therefore never splits a UTF-8 sequence or an extended grapheme cluster — for example a run of conjoining Hangul Jamo such as U+1100 U+1100 U+1161, which is one cluster although every character is a letter, an Indic conjunct (in Unicode versions whose rules join it), or a base letter with its marks — and never removes or alters the handle. If not even the first cluster fits, the title is the fixed ASCII `Untitled <kind>`, which always fits. The result is deterministic for a given input and pinned Unicode version; the pinned version is recorded in the export report, and changing it is a format-version change, because cluster boundaries and NFC can differ between versions. This document mandates no particular library: any implementation that conforms to UAX #29 and passes the Unicode `GraphemeBreakTest` data for the pinned version is acceptable, and SB-2 chooses one (an existing library, the platform's segmenter, or vendored tables). Basenames are NFC and unique case-insensitively across the whole export, because links resolve by basename. The relative path of every file inside the export is at most 160 bytes (folder names are short fixed ASCII). Extraction under a very deep path can still exceed a platform path limit; the export report says to extract near the top of a drive if that happens.
- **Links:** `[[<basename>|<title>]]`, unique by basename, never with a folder path, subpath or embed.
- **Each export is complete and fresh.** A title that changed since an earlier export simply appears under its new name in the new export; earlier exports are never modified. Users should keep their own notes outside exports.

## 6. Note format

### 6.1 Value classes

Every byte written belongs to one class, whatever path the data arrived by (UI, ordinary import, trusted restore or legacy migration — all are untrusted for rendering):

| Class | What | Where it may appear |
| --- | --- | --- |
| G | Generated constants (headings, banners, labels, fixed sentences) | Anywhere |
| E | Closed enums re-validated against the storage CHECK sets: kind, status, support, origin/actor, sensitivity, transitions | Prose, tables, frontmatter, tags |
| N | Exporter-computed numbers, booleans, handles | Prose, tables, frontmatter |
| T | Canonical times: a stored string matching `YYYY-MM-DDTHH:MM:SS+00:00` that parses, re-formatted by the exporter; anything else renders as the fixed *time not recorded*. The snapshot time is also class T | Prose, tables, frontmatter |
| S | Sanitized titles (§5) | Filename, H1, link display text, frontmatter `title` |
| L | Generated links between authorized items (§8) | Generated list items under predicate headings |
| U | Everything else: record content, claim text, decision notes, cited passages, `records.source`, nonstandard times, future descriptions | **Only** inside an inert block (§7) |

### 6.2 Frontmatter

Keys in fixed order: `sovereign_projection`, `sovereign_handle`, `sovereign_id` (only if the founder chooses to write canonical UUIDs, D13), `kind`, `title`, `status`, `support`, `authoritative`, `origin`, `sensitivity`, `created_at` (class T only), `provenance` (`partial`, §8, absent otherwise), `tags`, and future fields only once canonical (`claim_form`, `predicate`, `valid_from`, `valid_until`, `supersession_reason`). Navigation's Start Here alone carries `snapshot_at` and a class-level `scope`. Strings are double-quoted and escape-free by construction: every value must match its key's grammar, which excludes `"`, `\`, control characters, `[`, `]`, `|`, `#` and `://`; the emitter refuses anything else. One key per line, no folding. Tags only from the fixed vocabulary `sovereign/<kind>`, `sovereign/status/<status>`, `sovereign/support/<support>`, `sovereign/form/<form>`, `sovereign/navigation`. Never `aliases`, `cssclasses`, `publish`, `permalink` or any content-derived key. The demo vault's `available_after`, `future_fields` and `adversarial_fixture` keys are demo-only markers that an exporter never writes.

### 6.3 Banner and body

The first body block is the fixed banner, with the snapshot time as its only variable: *Snapshot of Sovereign taken ⟨snapshot time⟩, not live memory: it may be out of date, and forgetting something in Sovereign does not change this copy. Sovereign is authoritative; edits here are never imported. Lists and links only items included in this export; stored text is shown inert, with invisible or control characters as ⟪U+XXXX⟫. Scope: see Start Here.* (Start Here's own banner ends *Scope: below.*) Every note therefore labels itself even when copied out of the export. The demo vault's *(Synthetic demo.)* suffix and its fictional-disclaimer paragraph are demo-only. Then the H1 (title, optionally prefixed by a generated label such as "Decision:"), one status line built from classes G, E and T, the partial sentence when applicable (§8), and the **fixed section set of the kind**, each listing only included links, ordered by the endpoint's own time and handle, or the fixed *None in this export.*:

- **Source:** `## Content` (inert block), `## CORRECTS`, `## CORRECTED_BY`. A superseded revision says *superseded — no longer the current revision in Sovereign*, with no "by", date or pointer to the other endpoint.
- **Claim / decision:** `## Claim text` (inert), `## SUPPORTED_BY` (with each source's stored time and state), `## SUPERSEDES`, `## SUPERSEDED_BY`, `## Decision history` — a table of per-claim ordinal, stored time (class T), transition and actor only (never `claim_events.seq`), followed by each free-text decision note in its own top-level inert block, introduced by the generated label *Note on change N* with the note's stored length and line count; no generated text is ever placed inside a block, so a multi-line note cannot imitate another change's note. A stale claim says *evidence it cites has been corrected*, without saying which; an orphaned claim says its evidence is missing or fails its hash check.
- **Hub (after SB-3):** what a human filed here, grouped as current decisions, earlier decisions, claims needing attention, and sources, always with *Lists only items included in this export.*
- **Relationship (after SB-7):** subject, predicate (registry version), object, status; `## Why this connection exists` with one line per cited record and its cited passage in an inert block; decision history.
- **Navigation:** Start Here (snapshot time, class-level scope, legend — marking the orphaned group as appearing only when sensitive items are included — how to refresh, the Forget boundary of §11.2, that an export produced around an OS crash or power loss must be deleted and regenerated (§11.1), the generic explanation of partial notes), Timeline and status indexes; excluded from the graph by default.

**One canonical relationship, one link, one explanation.** The link sits in the note that holds the relationship (claim → sources; revision → predecessor; claim → predecessor claim; hub → members; relation → subject, object and evidence) under a heading naming the predicate. Reverse links are written only for lineage (`CORRECTED_BY`, `SUPERSEDED_BY`), so an outdated note points to its replacement when that replacement is included; everything else is reached through Backlinks.

## 7. Inert serialization of untrusted text (Codex F3)

Class U text is **data, never markup**. Only exporter code creates active Obsidian constructs. A blockquote is not enough: links, embeds, tags, HTML and callouts stay active inside blockquotes.

1. **Escape, never normalize.** Convert CRLF to LF. Replace with a visible `⟪U+XXXX⟫` marker: `⟪` itself; a lone CR; every control character except tab and LF (including NUL, VT, FF, DEL, C1 and NEL); U+2028 and U+2029; format characters (bidirectional controls, zero-width characters, BOM, soft hyphen, tag characters) and other default-ignorable code points; private-use and unassigned code points; combining marks after the third consecutive one. Neutralize plugin syntax that some plugins read even inside code blocks: a `%` preceded by `<` or `%` becomes `⟪U+0025⟫` (Templater, `%%` comments), and `::` becomes `:⟪U+003A⟫` (Dataview inline fields). Untrusted text is **never** Unicode-normalized: normalization can turn characters such as U+1FEF and U+FF40 into backticks.
2. **One top-level block per value.** Each U value is written as its own fenced code block with the info string exactly `text`, at document top level and column 0 — never inside a list, blockquote, callout, table, footnote or HTML — preceded by a generated label line stating the stored value's length in characters (counted before escaping) and the shown text's line count, and a blank line, and followed by a blank line and the generated line *End of stored text.*
3. **Unclosable fence.** The fence is backticks, one longer than the longest backtick run found in the escaped text **and** in its NFC, NFD, NFKC and NFKD forms (minimum 3).
4. **Forbidden placements.** U text, or anything derived from it other than through the title rule, never appears in a heading, paragraph, list item, table cell, link target or display text, inline code, callout, frontmatter, filename, folder name or `graph.json`.
5. **Generated constructs only.** Wikilinks only from the authorized edge set; no embeds, Markdown `[..](..)` links, autolinks, URLs or URI schemes, HTML, inline or body tags, footnotes, block IDs or comments are ever generated; callouts only the fixed banner and the fixed proposal warning. Since nothing generated references a network resource, any network request while viewing an export is a defect.
6. **Bytes.** UTF-8 without BOM, LF only, final LF; the same snapshot, export key, snapshot time, format version and pinned Unicode data version give byte-identical output.
7. **Output and plugin safety.** The output is a ZIP path or a folder that does **not** exist yet (Sovereign creates it). **Always refuse** an output inside a Git working tree; refuse one inside another Obsidian vault (any ancestor with `.obsidian/`) unless explicitly confirmed, in which case the preview lists that vault's enabled plugins; never write into an existing folder or over an existing file. Synced and network locations are refused on a **best-effort** basis: known sync-client roots and network or FUSE filesystem types from a pinned list are refused, any other destination gets a warning that its folder may be synced (and that the temporary file or staging folder is written there too), and the preview says that this detection is incomplete. The preview warns that opening an export in an Obsidian profile with community plugins that execute or upload note content (for example Templater with trigger-on-creation, AI assistants, sync) can run or copy it, and states that the guarantees cover core Obsidian plus the tested plugin versions only. Restricted mode is recommended.

## 8. Scope and reference closure (Codex F4)

An export must not reveal objects outside its scope through links, titles, filenames, handles, IDs, frontmatter, folders, navigation, metrics or its own logs.

1. **One snapshot.** The authorized set, every rendered byte and every count come from the single read snapshot of §11.1 — never from a cached index, graph or earlier export.
2. **Scope by class.** The user confirms a scope by filter class: kinds, statuses, a date range, sensitivity (default: private only), proposals (default: unreviewed `model` or `imported` proposals excluded). A time counts only if it is class T; an unparseable time fails every bounded range. A claim's sensitivity is computed exactly as the Context Compiler computes it; because missing or unverifiable evidence makes a claim count as sensitive, orphaned (unsupported) claims appear only when the user includes sensitive items, and a default export's orphaned section and color group are empty. Nothing is ever added to complete a link (**no widening**).
3. **Naming closure.** Remove every object whose rendered fields would name an object outside the set — today none; after SB-3/SB-7, relation claims whose subject or object is outside, hubs whose entity is outside — repeating to a fixpoint. The result is the authorized set **A**.
4. **Slots.** For each item in A, list only the slots it **holds**, from canonical columns: a record's predecessor and successors; a claim's evidence links, predecessor and successor. A `superseded` item with no successor in A has an out-of-set successor slot. Inbound edges are never slots: a record cited by an excluded claim is unaffected.
5. **OUT is one class.** Excluded, forgotten, missing, never-existing and malformed endpoints are treated identically, so forgetting an endpoint that was already outside A changes nothing.
6. **Edges.** Only in-set slots become links. Never compose edges: no transitive `CORRECTS`/`SUPERSEDES` across an omitted node, no "latest revision" shortcut, no link from a claim to a revision it never cited. `SUPPORTED_BY` links only to evidence whose pinned hash still matches (active or superseded); unverified or missing evidence is an OUT slot, which also keeps a squatted record ID from being linked to a genuine claim.
7. **Mode (D12).** *Label* mode: an item with an OUT slot carries the fixed sentence *"Provenance partial: at least one directly linked item is not included in this export."* exactly once, directly after the status line, never inside or next to a section, and gets `provenance: partial`; its sections list only included links or *None in this export.* *Closed* mode: repeatedly drop every item with an OUT slot until nothing changes, leaving the largest subset of A in which every slot held by a member points to a member, with no partial sentence. (Inbound edges are not slots, so an item is never dropped merely because an excluded claim cites it.)
8. **Wording.** The sentence and its surroundings never carry a count, title, handle, ID, date, status, sensitivity, kind word, relation word, reason or ordering word. Item status wording never refers to the other endpoint. Data attached to an omitted edge — such as the note and time of the transition into `superseded` when the successor is out of the set — is omitted as if absent. Completeness is never claimed: no "No corrections", "uncited", "original", "only source" or "no trace"; empty sections say *None in this export.* and every note says it lists only included items.
9. **Navigation and metrics.** Start Here, Timeline, status indexes and hubs are built from A and its edges only. A Timeline entry relates two objects only if both are in A; otherwise it shows the included object's own event; derived-state events ("became stale") appear only if their cause is in A. Start Here describes scope by class only and explains the partial sentence generically ("a filter, the date range, review status, sensitivity, or because the item is no longer in Sovereign"), never with examples. Health metrics, "most recent N" lists and counts are computed over A. Counts of excluded items appear only in the interactive preview, never in an export or a log.
10. **Invariant.** For two vault states that agree on A, on every A item's own row and events, on the edges and on the partial flags, an export made with the same export key and snapshot time is byte-identical, file for file. Nothing outside A influences any byte, filename or file count.
11. **Residuals stated in the preview.** Free text inside included items may mention excluded things (content, rendered inert); a partial sentence reveals that something linked is not included; an included item's own truthful status or support (for example *stale*) may reflect an excluded neighbour; someone who keeps successive exports can compare them and see changes. An included claim may also restate a superseded sensitive claim in its own text and title, because claim sensitivity follows evidence, not lineage (D15); the preview states this residual without naming any item, and opaque filenames reduce it. Closed mode reduces these.

## 9. Time in an export

- Statuses are "as of" the snapshot time stated in every banner and in Start Here.
- Revision and supersession chains are navigable both ways within the authorized set.
- Every claim note carries its decision history; Timeline lists stored, correction, approval, contest and supersession events of included items in order, under §8.9.
- Until SB-6, `superseded` is rendered as "no longer the current approved interpretation" and never as "false"; the supersession reason appears only once it exists canonically.
- Obsidian's *Animate* is not used to convey history (§3).

## 10. Making the graph meaningful in daily use

A graph is useful when a local neighborhood answers a question; a global hairball is decoration. Defaults:

- **Filter** `-tag:#sovereign/navigation`; **Tags** off; **Arrows** on; **Orphans** on (an item not cited by any claim in this export is informative).
- **Color groups, applied top-down, by generated tags only** (content cannot forge them, and folder-substring queries could be matched by titles): superseded (grey), rejected (charcoal), orphaned support (blue-grey), stale support (amber), contested (orange), proposed (purple), then projects, concepts, sources, decisions, claims, relationships. Every status and support state that is not approved memory therefore has its own color and never takes the color of its kind; the stale and orphaned groups match any status, so their labels never say "approved". The orphaned group is populated only in exports that include sensitive items (§8.2).
- **Start from a claim or source note (or, after SB-3, a hub) with Local graph, depth 1–2**, not from the global graph.
- **Health metrics reported at the end of every export, over A:** link resolution (must be 100%), orphan share, largest component share, maximum hub degree, share of readable titles.

`.obsidian/graph.json` is Obsidian's own, undocumented settings file. The exporter writes it only into the export it is creating, only with these constants, and Start Here repeats the settings for manual use.

## 11. The export operation and the Forget boundary (Codex F2, N1–N4)

One user-requested operation. It touches canonical state only by reading it (apart from the brief write lock, and possible schema migration, that every Sovereign process takes when it opens the vault). Filesystem writes are not atomic with SQLite and are not made to look so: the guarantees are that an export is rendered and verified completely before it is published, never replaces an existing destination, is reported as complete only after it is complete and verified, and states truthfully which snapshot it shows. What holds after something goes wrong depends on what went wrong — see *Outcomes by kind of event* below.

### 11.1 Steps

1. **Request and preview.** The user runs the export CLI. The preview shows the class-level scope (default: private items only — sensitive items and unreviewed proposals excluded), the filename mode, the output (a ZIP path or a new folder), counts of included items by kind and, interactively only, counts of excluded items; it states the residuals of §8.11, the plugin warning of §7.7 and the Forget boundary of §11.2. It refuses an output that already exists or lies inside a Git working tree, refuses one inside another Obsidian vault unless confirmed, and applies the best-effort sync and network check of §7.7. It also lists any recognizably named staging folders or temporary files beside the destination. Each is either the leftover of an interrupted export or belongs to an export still running, and the preview cannot tell which; the user may delete them once no other export is running, and the preview never deletes them itself.
2. **Snapshot.** Open the vault as every Sovereign process does (opening briefly takes the write lock and can migrate a legacy vault — existing behavior). Then open one read transaction (`BEGIN`), run its first read statement, record the snapshot time while that shared lock is held, read every row the export needs into memory, and end the transaction. That transaction is the **snapshot boundary**: a Forget, claim Forget or trusted restore that committed before its first read is absent from the export; anything that commits after it is not reflected. In rollback-journal mode, while the read is open, writes and new vault opens wait up to the 10 s busy timeout and then fail cleanly as busy, and new reads can queue behind a waiting writer. The read phase therefore only loads rows and ends well within the busy timeout (SB-2 measures it on its synthetic vault); no transaction stays open while files are written. **Preview binding:** if the authorized counts by kind or the include flags differ from the confirmed preview, stop and re-preview.
3. **Render** the complete export (§4–§10) in memory. For a folder output, write it into a fresh hidden staging folder beside the destination, in the same parent (`.<name>.sovereign-partial-<random>`, restrictive permissions). For a ZIP, no staging tree is written: the archive is built from the verified in-memory files (step 5). Staging and temporary files hold personal data (§12).
4. **Verify** the rendered export (§11.3): the staging folder for a folder output, the in-memory files for a ZIP. If any check fails, nothing is offered.
5. **Package**, never replacing anything. *ZIP:* write the archive to a hidden temporary file beside the destination (`.<name>.sovereign-partial-<random>.zip`, restrictive permissions), ask the operating system to flush it, read it back and check it against the verified files (a correctness check of what was written, not a durability check), then make it appear under the destination name with a primitive that fails if that name exists — a no-replace rename as for folders below, or a hard link to the destination followed by removing the temporary name; if none succeeds, the export fails (step 7). Entries are relative paths under one top folder, with UTF-8-flagged names, regular files only (no symbolic links, no absolute or `..` paths), in a deterministic order. *Folder:* move the verified staging folder to the destination name with a no-replace rename (Linux `renameat2` with `RENAME_NOREPLACE`, macOS `renamex_np` with `RENAME_EXCL`, Windows `MoveFileEx` without `MOVEFILE_REPLACE_EXISTING`). Where none is available, a folder export is refused and the user can choose a ZIP instead. Before the move, the exporter asks the operating system to flush every staged file and directory, including the staging folder itself (for example `fsync`, `F_FULLFSYNC` on macOS, `FlushFileBuffers` on Windows). This is a best-effort measure that makes damage after a crash less likely; it is **not** a durability guarantee, because filesystems, drives and their caches differ in what they persist and in what order. A plain `rename`, which can silently replace an existing empty folder, is never used. There is no copy fallback: if the move fails, the export fails.
6. **Report.** Only now report success: the output path, the snapshot time, the class-level scope, counts of included items and the health metrics (§10), with the fixed statements that the export is a snapshot outside Sovereign's control (§11.2) and that an export produced around an OS crash or power loss must be treated as potentially invalid and regenerated (*Outcomes by kind of event*). **Post-snapshot notice:** the exporter then reads the vault's tombstone counts once more; if they grew after the snapshot, the report says that something was forgotten, or restored with tombstones, after the snapshot was taken, that this export may still contain it, and that the user should delete the export and export again.
7. **On failure:** report the error, never success; remove this run's own staging folder or temporary file on a best-effort basis; leave nothing under the destination name. No export deletes anything but its own staging and temporary files, and later exports only list recognizably named leftovers for the user, without distinguishing them from a run still in progress (step 1). The next export simply starts fresh.

**Outcomes by kind of event.**

1. **Normal completion:** the complete, verified export is under the destination name, nothing was replaced, and success is reported with the snapshot time.
2. **Process interruption or termination** (the exporter is killed or crashes while the operating system keeps running): nothing is reported. Because the destination name appears only through the final no-replace move or link of already-verified content, nothing partial or unverified appears under it; a hidden, recognizably named staging folder or temporary file may be left beside it. A run stopped after its final move but before its report can leave a complete, verified export that was simply never reported.
3. **Operating-system crash, power loss, or filesystem or hardware failure:** **no guarantee.** Depending on the filesystem, the drive and its cache, files of an export written around such an event — under the destination name or beside it — may be missing, empty, damaged or only partly persisted, even though flushes were requested and a move succeeded. Sovereign keeps no record of exports and cannot detect this afterwards. **Any export produced around such an event must be treated as potentially invalid: delete it and export again.** The export report and Start Here say so.

### 11.2 Forget and the snapshot boundary

- **Canonical Forget is unchanged** (ADR-0003): it removes the item, and everything derived from it, from Sovereign's governed vault.
- **A new export reflects its snapshot.** Items forgotten before the snapshot boundary are absent, and an export never describes itself as later than its snapshot time. An export made before a Forget is never presented as the post-Forget vault.
- **An earlier export is an independently held artifact.** Sovereign cannot erase an export that was already downloaded, extracted, copied, synced or backed up, and does not try: it keeps no list of exports and, apart from opening the vault as every Sovereign process does (step 2), never modifies or deletes anything outside the staging folder, temporary file and destination of the export it is currently producing. Obsidian's own caches, file-recovery snapshots and `.trash`, OS search indexes, sync services and plugins can hold further copies.
- **Disclosure.** The Forget preview and result and the export preview and report say plainly that "forgotten in Sovereign" never means "deleted from your exports": earlier exports and hidden leftovers of interrupted exports are outside Sovereign's control, and the user deletes those files and exports again. Every note's banner and Start Here state the snapshot time and that forgetting in Sovereign does not change the copy; Start Here also tells the user to delete exports they no longer need and export again. No secure deletion is claimed for exports, staging remnants or temporary files.
- **Concurrent mutations.** An export is consistent at its snapshot boundary only; a mutation that commits during rendering or packaging is not reflected. The post-snapshot notice reports a later Forget or trusted restore when the tombstone counts show it. It is a courtesy, not a guarantee: under the open storage defect (SECURITY-GATE), raw SQL can replace a tombstone without changing the counts.

### 11.3 Verification before an export is offered (Codex N3, N4)

Verification checks the export's **structure** against the exporter's own model of what it intended to write. It never searches free text for excluded identifiers.

- **Files:** the set of files equals the set derived from A (one note per item, the navigation notes, `graph.json`, the marker), and nothing else.
- **Filenames (N4):** every basename is valid NFC UTF-8 within the byte limit of §5, unique case-insensitively, and ends with its item's own handle; every relative path is within its limit.
- **Frontmatter:** keys from the schema, in order; every value matches its key's grammar and equals the expected value for that item (handle, title, status, support, authority, origin, sensitivity, time, provenance flag, tags).
- **Generated text:** each note's sequence of elements equals the expected skeleton for its kind — banner first, H1, status line, the partial sentence at most once and only in its fixed position, the fixed sections in order — and every interpolated value (title, enum, time, number, state, decision-history cell, inert-block label) equals the value computed for that item from A and the snapshot rows. Every inert block is top-level, carries its label and trailer, and holds exactly the escaped stored value it was rendered from (§7). `graph.json` and the marker equal their expected bytes.
- **Links:** every wikilink outside inert blocks is a generated list item whose target is the basename of an item in A, whose display text is that item's title, and whose (source, slot, target) is an authorized edge (§8.6); each note's links equal its authorized edges.
- **Navigation and metrics:** every entry refers to an item in A, and every number is computed over A.
- **No free-text scan.** Excluded IDs, titles and content are not searched for in rendered text: identifiers can coincide with ordinary words (legacy and imported IDs are arbitrary text, and titles repeat), so such a scan would block legitimate exports while missing the structural leaks the checks above catch. Only exporter-generated links can create Obsidian graph relationships; untrusted text stays inert inside its blocks (§7). Random canaries that cannot collide are used in tests, not at run time (validation spec §4.3).
- **On failure:** stop, report the failed check by file handle and check name only, and offer nothing.

### 11.4 What V0 deliberately does not do

- No persistent projection registry, per-file ownership hashes, multi-generation ledger or list of exports.
- No SQLite write lock held during filesystem work; no claim that a multi-file publication is atomic, that flushing or rename ordering makes it durable, or that it survives an OS crash or power loss; no cross-process recovery protocol.
- No automatic, background, scheduled or Forget-triggered cleanup, reconciliation or regeneration of exports.
- No cleanup of other runs: an export never deletes leftovers of earlier interrupted runs; it lists them for the user.
- No in-place refresh: an export never writes into an existing folder or over an existing file. Replacing a Sovereign-generated folder may be proposed later as a separately evaluated operation, with explicit user confirmation and safe handling of notes the user edited or added (D9).
- No import of edits (§13).

### 11.5 Superseded design and Codex N1–N2

Revision 2 of this spec specified a **managed projection**: a registry of owned files and hashes beside the vault, the vault write lock held from snapshot to final directory sync, registration before writing, verify-and-promote crash recovery and automatic reconciliation after every Forget (preserved in commit `11b2f4b`). The founder's 2026-10-20 direction makes the export a snapshot instead, so:

- **N1 (multi-version ownership recovery) does not apply:** there is no registry, no multi-generation hash ledger and no ownership recovery. An export is written once into a fresh location and never revisited.
- **N2 (crash atomicity and generation consistency) is resolved by not claiming either:** a failed export is reported as failed; on process interruption nothing is reported and nothing partial or unverified appears under the destination name; after an OS crash, power loss or storage failure nothing is guaranteed and the export must be treated as potentially invalid and regenerated (*Outcomes by kind of event*, §11.1). Nothing promises atomic multi-file visibility, physical durability, crash recovery or consistent generations across runs; the next export starts fresh. Staging, best-effort flushing, no-replace publication, failure reporting and verification remain.
- **Codex F2's race** — an exporter publishing a pre-Forget snapshot after Forget cleanup — no longer breaks any promise: exports do not claim to follow Forget, every export states its snapshot time, and a Forget after the snapshot is disclosed (§11.2).

## 12. Privacy and boundaries

- Local only. The CLI writes only the output the user named, plus that run's own hidden staging folder or temporary file beside it, never into an existing file or folder. Sovereign enables no Git, Obsidian Sync, cloud drive, publishing or plugin; opening an export in an Obsidian with sync or plugins configured may copy it, and the preview says so.
- Sensitive items are excluded by default; including them requires an explicit flag and forces opaque filenames for those items. While the Security Gate is NOT PASSED, exports are produced and tested with synthetic or deliberately non-sensitive data only.
- No raw canonical ID is written by default (D13); handles are keyed per export. Titles and content are still personal data, which is why an export must not be synced or published by default.
- Staging and temporary files are created with restrictive permissions beside the destination (so the Git-tree, vault and sync checks cover them too) and removed on a best-effort basis; an interrupted run can leave one behind, and no secure deletion is claimed.
- Logs and messages identify items by handle and counts only, never by title or content.
- **A UI button (later)** must call the same operation and return the ZIP as a download to the requesting page; it never writes to a path chosen by an HTTP request. The local HTTP API has no authentication, so that endpoint, which would hand every included note to any client able to call it, needs its own threat review first.

## 13. Edits

Exports are one-way. Sovereign never imports edits made in Obsidian and never modifies an export after reporting it. Notes the user edits or adds inside an export stay the user's; a new export goes to a new location and leaves the old one untouched. A governed import of edits would need its own ADR.
